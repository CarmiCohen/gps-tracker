# JD project - standing session instructions

These apply to every session automatically; the user does not need to repeat them.

- **Start**: read only `DOCS/issues.md` (the index: Resumption State, Status, Focus, queue) and `chat_session.md` if it exists; take the next Focus item unless the user names another, read just that item's section of `DOCS/issue_details.md`, and display the issue before fixing it (Rule 1). Do not read `DEVELOPER_GUIDELINES.md` at the start: the essentials are below; open it (targeted, D7) only for a rule's exact wording or at the Completion Sequence. `DOCS/operational_notes.md` only for device work.
- **Rules**: `DEVELOPER_GUIDELINES.md` still applies, including D1 to D7 and the 6-step Completion Sequence. Essentials: root-cause fixes, no workarounds; every fix comes with automated tests named in the commit message (Rule 15); never remove a test without the user's confirmation (Rule 17); a resolved item is removed from the index and from `issue_details.md` (Rule 5); new risks become one Open Gap line plus a details section (Rule 4). The archive, SOT, baseline index, dashboard and audit line are frozen at Nov23.4: never write to them (user decision 2026-11-23).
- **Git**: at Completion step 5 Claude commits, tags and pushes the main repo itself, without asking (user decision 2026-11-19); the commit message is the version's record (D1); never force-push.
- **Session log (D6)**: `chat_session.md` (git-ignored) is a short, append-only milestone log, kept only in sessions that change code or device state (user decision 2026-11-27, O171): decisions, test results, next steps, temporary device state to restore. Delete it at Completion step 5.
- **Version name**: use the name the user gives; otherwise ask once.
- **Token economy** (user decisions 2026-11-23 and 2026-11-27, O171):
  - One Completion Sequence per session; small related items may share it. After the Final stop, suggest `/clear`; also suggest `/clear` when the user switches to an unrelated topic or question.
  - Only the user can change `/effort` or `/model`: recommend it once, when displaying the chosen issue, then carry on. `/effort low` (and `/model sonnet`): bookkeeping, documentation-only versions, simple device checks, running tests. `/effort high`: new features or tricky fixes (new sensor logic, thresholds, concurrency, Android platform rules, performance traces). Otherwise medium.
  - **Answers**: short by default; details only on request. Progress notes one short line.
  - **Tests while working**: only the affected test classes, with quiet output, e.g. `gradlew -q :core-shared:test --tests "com.jd.core.shared.MotionSentinelTest"` or `:app-monitor:testDebugUnitTest --tests "*TrailPruning*"`; on a phone `am instrument -e class <class>`. The full unit suite once, at Completion step 1, through `TESTS/run_tests.ps1` (one summary line). Phone tests only for the classes related to the change.
  - **Code comments**: a short "what and why"; no history (issue lists, dates, measurements, user decisions), which belongs in the commit message. Keep the issue ID of the change (Rule 13). Trim old history comments only in files a version touches anyway.
  - **Tool output**: filter logcat by tag, read files in line ranges, never re-read a known file.
- **Phones**: test on the A15 (`R58X40GV2AR`); the S21FE is in personal use. When both are connected, use the Two-phone test of `DOCS/operational_notes.md` (Sensor on the A15, Monitor on the S21FE) without asking the user (user decision 2026-11-17, Nov17.4); still check the S21FE's foreground app first.
