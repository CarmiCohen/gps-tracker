## 🚀 Strategic Simplification Ideas
*   **SIMP-NOV17.7-S1**: Unknown Temperature As Null. `LocationUpdate.tempCelsius` uses -1 for not known (and the forensic buffer stores it so since Nov17.7), which is also a real temperature, and `LocationRowWire.decode` reads a missing `temp` as 0 and `batt` as 0. A nullable temperature and battery, left out of the row when not known like the satellites, would give one meaning to each value; the Monitor's checks (`tempCelsius > 0f`, `batteryLevel >= 0`) would read `null` instead.
*   **SIMP-NOV17.6-S1**: Trail In The Device Color. Since Nov17.6 the map shows the Sensor as a green dot and the Monitor as a cyan dot, and the Monitor's own trail is cyan, but the Sensor's trail is still `Color.BLUE`. Drawing it in the Sensor green would tie trail and dot together; it is kept blue for now (user decision 2026-11-17) because the Home Point circles use the same green.
*   **SIMP-NOV15.5-S1**: One Status Place. Since Nov15.5 the Info screens show the service, microphone, motion and relay states, and the Sensor's Setup dialog still repeats them as text lines (`serviceStatusText`, `relayStatusText`, `microphoneStatusText`, `motionStatusText`), as does the Sensor console. The Setup dialog could keep only IDs, relay URL and its buttons, with a link to Info, so each state has one wording and one place.
*   **SIMP-NOV15.3-S1**: One Settings Decoder. Six message types (`GeofenceWire`, `SensorBehaviourWire`, `SensorSetupWire`, `SensorEventsWire`, and since Nov15.5 `SensorInfoWire` and `InfoRequestWire`) share the relay's `settings_update` / `settings_relay` event, and each `decode` checks `type` and returns null for the others, so `settings_relay` runs all of them on every message. One `SettingsWire.decode(data): SettingsMessage?` with a sealed result would dispatch once and keep the type names in one place.
*   **SIMP-NOV10.8-S1**: One Overlay Header. Each `core-ui` overlay (`PhoneSetupOverlay`, `CleanSetupOverlay`, `AlertManagementOverlay`, `AlarmSoundOverlay`, `ToolsOverlay`, the Sensor's `SettingsOverlay`) builds its own title row and close control, and only Phone Setup got the `weight(1f)` title in Nov10.8. A shared `OverlayHeader(title, onClose)` that also registers the overlay's `BackHandler` would keep the X on screen everywhere (ISSUE-NOV10.7-O74) and move the per-call-site handlers of ISSUE-NOV10.8-O78 into one place. With it, extend `SetupNavigationTest` (chapter 178) to Back on Alerts, Sound, Clean Setup, Tools and Home Point editing (only Phone Setup is automated; the Sensor's Back is a hand check, 178.3).
*   **SIMP-NOV9.3-S1**: Faster Release Starts. The release builds are unminified and ship no baseline profile, so a fresh install starts on JIT only (Monitor about 0.45 s on the A15). Adding `androidx.profileinstaller` would let the baseline profiles the Compose libraries already ship be compiled ahead of time; R8 would come later, with keep rules for Hilt, Room, and osmdroid.
*   **SIMP-NOV9.3-S2**: Keep The Virtual Peer. The Nov9.3 reciprocal simulation used a small Node script (Socket.IO v4 over the built-in WebSocket: a virtual viewer and a virtual tracker against the production relay), kept outside the repository. As `TESTS/virtual_peer.mjs` with a one-line summary, a one-phone session could repeat it instead of rewriting it.
*   **SIMP-NOV9.1-S1**: One Telemetry Encoder. `SocketioSignalingClient` builds the telemetry JSON twice, in `sendTelemetryBatch` and `sendBackfillResponse`, and parses it once; Nov9.1 added `noiseOff` to the live copy only. One `encodeTelemetry(update)` in `LocationRowWire`, next to its `decode`, would keep the fields in step (the buffer decides what a backfilled row can carry).
*   **SIMP-NOV8.103-S1**: Violation Priority In The Sensing Loop. Since Nov9.0 one `reportViolation` helper sends every violation, but a movement verdict still silently overwrites a geofence status on the same tick. An explicit priority (or queueing the second like the sensor alerts) would keep both; with SIMP-NOV8.13-S2 it could also drop the unused violation event.
