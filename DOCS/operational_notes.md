# Operational Notes (device and test procedures)

*Read only for device work or instrumented runs, and only the note needed (D7). Moved out of `DOCS/issues.md` in Nov27.5-docs (ISSUE-NOV27.5-O171).*

- **Instrumented runs wipe the Monitor too** (Nov10.8; it happened again to the Sensor in Nov16.4: never use `connectedDebugAndroidTest` on the A15, always the `am instrument` way at the end of this note, and with the S21FE connected pin every Gradle install with `$env:ANDROID_SERIAL='R58X40GV2AR'`, as `installDebug` installs on every connected phone): `connectedDebugAndroidTest` on either app uninstalls it afterwards, deleting its data, pairing and runtime permissions. Restore on the A15 with `adb shell pm grant` (Sensor: fine, coarse and background location, `RECORD_AUDIO`, `POST_NOTIFICATIONS`, and `cmd notification allow_listener com.jd.app.sensor/com.jd.app.sensor.SilentNotificationListener`; Monitor: fine and coarse location, `POST_NOTIFICATIONS`), then `device_check.ps1 -App sensor -Command SET_ID -Id T` and `-App monitor -Command PAIR -Id T` with each app in front. Home Points, the detection settings revision, the battery exemption (`dumpsys deviceidle whitelist +<package>`) and the Events lists (Nov15.4) are lost; the tests write their own event files. To keep everything, install the test APKs (`:app-sensor:installDebugAndroidTest`, `:app-monitor:installDebugAndroidTest`) and run `adb shell am instrument -w <package>.test/<package>.HiltTestRunner` (add `-e class <test class>` for one class).
- **Pushes during instrumented runs** (Nov19.4, ISSUE-NOV12.3-O90): Monitor runs need no airplane mode any more; `HiltTestRunner` turns `MonitorMessagingService` off for the run and back on at its end. If a run kills the process before it ends, the installed Monitor gets no push until the next run ends or it is reinstalled: check `adb shell dumpsys package com.jd.app.monitor | grep disabledComponents` (nothing expected), or `adb shell pm enable com.jd.app.monitor/.MonitorMessagingService`. A freshly installed Monitor needs `pm grant com.jd.app.monitor android.permission.POST_NOTIFICATIONS` before a full run (`SensorSetupNoticeDeviceTest`).
- **Sensor service restart**: an install over the Sensor restarts its service by itself (Nov12.7, `MY_PACKAGE_REPLACED`). Instrumented test runs uninstall the Sensor app; reinstall it with `:app-sensor:installDebug`, then open the app once. Running an installed test APK with `adb shell am instrument` keeps the app and its data but force-stops it; opening the app (`adb shell am start -n com.jd.app.sensor/.AdminActivity`, no tap needed) restarts it with the microphone (Nov12.7).
- **Both apps on one phone**: the Sensor microphone can hear the Monitor siren; the noise alarm stays one pending alarm until acknowledged. Since Nov9.4 the siren is also the phone's own sound to `OwnVibrationWatch`, so vibration is ignored while it plays (`REV_Motion: Phone ringing or notifying`); knock tests wait until the siren stops. An incoming call's screen also stays in front of the Monitor's alarm screen.
- **How late a Monitor hears the Sensor** (Nov11.0): `adb logcat -d -s REV_Signaling:*` shows `Alert row ... arrived N ms after it was sent` and a 10 s `Arrival lag ... mean, max` line (release builds log it too); compare the same `seq` on both Monitors. Normal on the A15: about 0.5 s mean, alerts about 0.3 s. Across two phones the lag includes their clock difference (Nov19.1: the S21FE ran 1.2 s ahead of the A15, so 1.8 s logged was about 0.6 s); measure it with `adb -s <serial> shell date +%s%3N` on both. Since Nov22.8 a Sensor sends at most one row a second (moving, on outside power, or within 5 min of an alarm) and one per 10 s otherwise (O133, O136), so about 10 rows per 10 s is the most.
- **Alarm push** (Nov11.1-push): `https://gps-survival-relay.onrender.com` must say `push: on` (Render env `FIREBASE_SERVICE_ACCOUNT` holds the key file's whole JSON content, not its name); `adb logcat -d -s REV_Push:*` shows `Alert row ... arrived by push N ms after it was sent`. Never `am force-stop` the Monitor before a push test: Android delivers no push to a stopped app until it is opened. The relay repo (`relay-server`, `gps-survival-relay`) is committed and pushed separately; Render does not deploy on push: the user runs Manual Deploy, Deploy latest commit (Nov11.2-relay), then the page shows a small `uptime_s`. A relay restart forgets the tokens: open the Monitor once before a push test. The silence notice logs `REV_Push` `Relay notice by push: tracker 'T' sent nothing for 35 s (last row seq N)`.
- **Silencing the Sensor for a test** (Nov11.2-relay): `am force-stop com.jd.app.sensor` does not work, Android rebinds its notification listener 120 ms later and the service starts again. Cut its network instead: `adb shell cmd connectivity set-chain3-enabled true` then `set-package-networking-enabled false com.jd.app.sensor`; restore with `set-package-networking-enabled true com.jd.app.sensor` and `set-chain3-enabled false` (the A15's chain3 was disabled). Cut this way, the Monitor raises Local internet lost at once, with the siren (Nov18.12). From PowerShell quote the whole shell command, `adb shell "dumpsys deviceidle whitelist -com.jd.app.sensor"`: unquoted, `-com...` is split as a parameter.
- **Two-phone test** (user decision 2026-11-17): when both phones are connected, the device tests run with the Sensor on the A15 and the Monitor on the S21FE. Do not ask the user (user decision 2026-11-17, Nov17.4); the S21FE is in personal use, so check its foreground app first, never capture or send input while a personal app is in front, and note its state in `chat_session.md`. Install the debug Monitor on the S21FE and the debug Sensor on the A15, uninstall the Monitor from the A15 (`adb -s R58X40GV2AR uninstall com.jd.app.monitor`), pair the two, then follow the logcat of both phones and the Monitor's event log during the test. Afterwards restore the S21FE as in the next note; the A15 Monitor is installed again only when an A15-only test needs it.
- **S21FE Monitor test** (Nov12.0-push): the user keeps its Monitor unpaired and Global Mute on; pair it to `T` and turn the mute off for the test (alarm volume 0 keeps it quiet), then restore both. Open the Monitor with the screen on (`input keyevent WAKEUP` first): the session starts at the screen's first draw, so launched with the screen off it never starts and the relay has no push token. Use the debug build for `REV_` lines (it installs over the debug-key-signed release and keeps the data); finish with `install_release.ps1 -Serial R5CRC14PG4F -Apps monitor`. The layout is right-to-left: find buttons by `uiautomator dump` bounds (`Setup`, whose dialog holds `UNPAIR`).
- **Remote check of the Sensor**: `device_check.ps1 -App sensor -Command STATE` answers `mic=`, `motionArmed=`, `vibrationArmed=` (Nov9.2), `refusedLocation=`, and `refusedMic=`; a resting A15 arms 30 s after the Sensor starts (Nov9.0), counted from the last touch, so the tap that starts the service delays it.
- **Reboot test on the A15** (Nov9.1): the boot broadcast reaches the Sensor about 1.5 min after `adb reboot`; `dumpsys activity services com.jd.app.sensor` shows the held types (`0x289` all, `0x209` without the microphone, `0x201` neither). On the Samsung lock screen the first tap on a notification only selects it; the second opens it. The A15 now has "Allow all the time" location, so a reboot keeps location; revoke it in the app's location settings to repeat chapter 163.3. The Monitor is not started at boot.
- **Debug `PAIR` while paired** (Nov9.3): the Monitor's session reads its target once, so `PAIR` from one tracker to another leaves the session on the old one. Run `UNPAIR` first, then `PAIR`, with the Monitor screen in front (not under the notification shade), and look for `REV_MonitorService: Connecting to relay ... for target <id>`.
- **Long device runs** (Nov10.2): the A15's main logcat buffer rolls over in under 30 minutes (a `Telemetry sent` line every 10 s plus system output). For a run longer than a few minutes, stream `adb logcat -v time -s REV_SensorService:* REV_Motion:*` to a PC file from the start.
- **Startup frames** (Nov9.3, ISSUE-NOV8.13-O55): debug builds run in ART's interpreter (Monitor first frame about 730 ms); the frame audit uses the release builds from `TESTS/install_release.ps1`, then `installDebug` restores the debug builds.
