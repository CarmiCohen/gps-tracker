*   **1.357 Forensic Entry Integrity (R-ID 128)**: Each `ForensicBuffer` entry MUST carry a checksum and damaged entries MUST NOT be returned; a sent sequence number MUST NOT be reused after power loss; a file format upgrade MUST keep stored entries; and code in `core-shared` MUST call only methods available at the Sensor's `minSdk` (R-ID 128).
*   **1.358 Real HUD Values (R-ID 129)**: Both Monitor HUD lines MUST show only real readings. The local line MUST use the Monitor device's own battery and position fix; a value that is not known MUST show as `--`, never as an invented number; and local speed MUST NOT be shown from a fix older than 35 seconds (R-ID 129).
*   **1.359 Bounded Trail Storage (R-ID 130)**: The Monitor MUST keep at most the newest 50,000 stored trail rows of each tracker, enforced by a background job scheduled at app start. Remote rows MUST be limited by count, never by age, so a tracker always keeps its newest rows and pruning never causes a false backfill (R-ID 130).
*   **1.360 Real Relay Status Text (R-ID 131)**: The Monitor Setup dialog MUST report the relay connection from the same state that drives the `SRV` LED, and MUST NOT show a fixed status or claim a connection it does not know (R-ID 131).
*   **1.361 Backfill Gap Recovery (R-ID 132)**: The Monitor MUST find missing telemetry from its stored trail, so a range that could not be requested or was never answered is requested again; a limit on requests MUST delay a range, never lose it; an unanswered request MUST be released; and the signaling client MUST NOT drop updates during a reconnect burst (R-ID 132).
*   **1.362 Real Version Strings (R-ID 133)**: Every version shown or logged by either application MUST come from the installed package. A version that cannot be read MUST show as `--`, and production code MUST NOT hold a release version in a string (R-ID 133).
*   **1.363 Unpair Confirmation (R-ID 134)**: No Monitor control MUST clear the pairing in one tap. Every control that unpairs MUST open one confirmation that names the tracker, and only its confirm action MUST clear the pairing; cancelling MUST keep it (R-ID 134).
*   **1.364 Real Sensor HUD Values (R-ID 135)**: The Sensor HUD MUST show the motion state, speed, accuracy, and age of the fix the Sensor service last received, using the same rule as the Monitor local line (rule 1.358). With the service stopped or before its first fix, these values MUST show as `--`, never as an invented number (R-ID 135).
*   **1.365 Monitor Alarms And Siren (R-ID 136)**: While a tracker is paired, the Monitor MUST raise an alarm when the tracker sends nothing for 35 seconds, reports no charging, reports a battery below 20%, or reports a temperature above 46°C, each only while its Alert Settings switch is on and Global Mute is off. An alarm MUST show full screen and sound the siren, with the saved Siren & Audio settings, until it is acknowledged, and MUST be raised again only after its condition has cleared. The alarm notification MUST use a high-importance channel that no other code can lower, and the Sensor MUST NOT play sound or vibrate (Rule 14, R872) (R-ID 136).
*   **1.366 Communication Alarms (R-ID 137)**: The Monitor MUST raise communication alarms for `Relay disconnected` when relay socket connectivity is lost (`signalingClient.isConnected` false; before the first connection only as rule 1.375 allows), `Monitor internet lost` when local internet network capabilities report no active internet connection, and `Tracker GPS signal loss` when telemetry from the paired tracker reports `(0,0)` coordinates, 0 accuracy, or a `NO_FIX` / `GPS_SIGNAL_LOSS` status while online, for 30 seconds (rule 1.375). Each MUST be switched by its respective Alert Settings toggle (`relayConnection`, `localInternet`, `signalLoss`) and Global Mute, sounding until acknowledged (R-ID 137).
*   **1.367 30-Second Siren Auto-Stop (Timer or Acknowledge) (R-ID 138)**: The Monitor siren MUST automatically stop after 30 seconds (`30s`) or when acknowledged, whichever occurs first. When the siren auto-stops via the 30-second timer, the visual alarm and notification MUST remain pending until explicitly acknowledged by the user (R-ID 138).
*   **1.368 False MOVING Fix & Sensor-Detected Violations (R-ID 139)**: The Sensor MUST run `SentinelLogic.validateMovement` with accelerometer motion (`hasPhysicalMotion`) once on each new fix (rule 1.375) to suppress GPS drift and false MOVING while stationary, and MUST transmit its motion state and violation status (`JUMP`, `OUTLIER`) in telemetry and via `ViolationEvent`. The Monitor MUST raise a GPS jump alarm (`AlarmType.GPS_JUMP`) when a violation or jump status is received, following `AlertSettings.jammerDetection` (R-ID 139).
*   **1.369 HUD Flow Rate-Limiting (R-ID 140)**: The Monitor `localHudState` and `remoteHudState` flows, as well as the Sensor `hudState` flow, MUST apply `atUiRate()` (500ms sampling window) to incoming telemetry and fix streams, capping UI state recalculations and emissions to at most 2Hz to prevent excess CPU usage, unnecessary IPC calls, and rapid recomposition (R-ID 140).
*   **1.370 Screen State & Rotation Preservation (R-ID 141)**: All UI overlay visibility flags, dialog states, and map follow modes in `MonitorActivity` and `AdminActivity` MUST use `rememberSaveable` to ensure open overlays, dialogs, unlock states, and follow modes persist across screen rotation and configuration changes (R-ID 141).
*   **1.371 Thread-Safe Signaling Queue & Order-Preserving Failed Flush (R-ID 142)**: The signaling queue (`SignalingQueue`) MUST perform all queue manipulations and sequence tracking under a `ReentrantLock` for multi-threaded safety between telemetry offering and queue flushing. When a batch flush fails due to a network disconnection or transmit failure in `SocketioSignalingClient`, the un-sent updates MUST be re-queued at the front of the queue (`pushFront`) in their exact original sequence order to prevent reordering behind newer incoming updates (R-ID 142).
*   **1.372 Coarse Network Fix Filtering (R-ID 143)**: `MonitorLocationSource` MUST filter incoming location updates using `isBetterLocation` to prevent a coarse Network location fix (e.g., accuracy ±77.6m) from replacing a fresh, more accurate GPS location fix (e.g., accuracy ±11m) on the Monitor UI and map. A coarse Network fix MUST only replace a GPS fix if the GPS fix is older than 2 minutes (120s) (R-ID 143).
*   **1.373 Backfill Answer Stops On Send Failure (R-ID 144)**: The Sensor MUST answer a backfill request in chunks of at most 50 rows and MUST stop at the first chunk that `sendBackfillResponse` fails to send. After a failed chunk it MUST NOT send any later chunk of that request, including the completion chunk (`isComplete`), so the Monitor never counts a range with missing rows as answered; the Monitor's 30-second request release and stored-trail gap scan (rule 1.361) then request the remaining rows (ISSUE-NOV6.4-O33) (R-ID 144).
*   **1.374 Real Sensor Service Status (R-ID 145)**: The Sensor Setup dialog MUST show the service state reported by `SensorService` itself through the `@Singleton` `SensorServiceStatus` (running only after `initializeServiceComponents` has started the service components, stopped again in `onDestroy`) and the relay state from `SignalingClient.isConnected`, as `Sensor Service: Running` / `Stopped` and `Relay Connection: Connected` / `Disconnected`. No screen may show a fixed service state such as `Active / Ready` (ISSUE-NOV6.4-O34) (R-ID 145).
*   **1.375 No False Alarms At Start (R-ID 146)**: The Monitor MUST NOT raise `Relay disconnected` for a relay it has not yet connected to until 30 seconds after it starts watching (`RELAY_FIRST_CONNECT_GRACE_MS`); after a connection, a lost relay MUST raise it at once. `Tracker GPS signal loss` MUST be raised only after the tracker has reported no position for 30 seconds (`GPS_SIGNAL_LOSS_AFTER_MS`). The Sensor MUST check movement once per new fix, against the previous fix and timed by the fixes' monotonic clock, never on loop ticks that send the same fix again; `SentinelLogic.validateMovement` MUST treat a move smaller than the larger of the two fixes' accuracies as `VALID`, and a `JUMP` reason MUST carry the measured speed, distance, interval, and accuracies. A `ViolationEvent` MUST be built before its send is launched, from a copy of the update (ISSUE-NOV7.17-O42) (R-ID 146).
*   **1.376 Real GPS Loss Reporting & Explicit Critical Delivery (R-ID 147)**: Whether a telemetry update is sent unbatched, kept when the queue overflows, and exempt from sequence deduplication MUST be decided only by `LocationUpdate.isCritical`, never by the text of its `status`; the flag stays with the sender and is not sent. The Sensor MUST set it only for an update carrying a violation (`JUMP`, `OUTLIER`), and MUST commit such an update to the forensic buffer at once. The Sensor MUST send `NO_FIX` with no position (latitude, longitude, and accuracy 0) on every tick while it has no fix, or while its newest fix is at least 15 seconds old (`FIX_STALE_AFTER_MS`, measured on `elapsedRealtimeNanos`), and MUST NOT send an older fix as current. It MUST NOT judge movement on, or keep as the reference, a fix whose accuracy is unknown or coarser than 100 m (`MOVEMENT_CHECK_MAX_ACCURACY_M`) (ISSUE-NOV7.19-O43, SIMP-NOV7.19-S1) (R-ID 147).
*   **1.377 Sensor Battery State Seeding & Unknown Guarding (R-ID 148)**: `SensorService` MUST capture sticky `ACTION_BATTERY_CHANGED` broadcast intent returned by `registerReceiver` prior to starting `startSensingLoop()`, seeding initial charging state, battery level, and temperature to prevent false `POWER_DISCONNECTED` sirens when starting Sensor service while Monitor watches. Monitor alarms MUST guard battery level (`batteryLevel >= 0`) and temperature (`tempCelsius > 0f`) checks against unknown/uninitialized values (ISSUE-NOV7.21-O45, ISSUE-NOV7.2-O37) (R-ID 148).
*   **1.378 Sensor PermissionGuard Re-check On Resume (R-ID 149)**: `PermissionGuard` in `AdminActivity` MUST observe `Lifecycle.Event.ON_RESUME` using `LocalLifecycleOwner.current` and `DisposableEffect`, re-evaluating `checkSensorPermissions` so that returning to `AdminActivity` after granting permissions in system Settings or external permission flows immediately updates `allGranted` state without requiring button re-clicks (ISSUE-NOV7.19-O44) (R-ID 149).
*   **1.379 Sensor Siren Test Button Disabled On Stealth Tracker (R-ID 150)**: The Sensor MUST NOT display an interactive local siren audio test button (`TEST SIREN AUDIO`) in its Siren & Audio setup overlay when acting as a stealth tracker (`isTracker = true`), enforcing Rule 14 (Stealth Authority, R872) at the UI component level (`AlarmSoundOverlay`) (ISSUE-NOV7.3-O38) (R-ID 150).
*   **1.380 Real Telemetry Unknown Values Handling (R-ID 151)**: `SensorService` MUST verify `loc.hasSpeed()` before copying speed into telemetry, transmitting `-1f` when speed is unknown, and MUST NOT invent initial battery level or temperature before broadcast intents arrive. `MonitorViewModel` and HUD renderers MUST treat negative speed/battery and non-positive temperature as unknown (`--`), preventing false alarms (ISSUE-NOV7.2-O37) (R-ID 151).
*   **1.381 Alarm Reach Under Do Not Disturb & Locked Screen Setup (R-ID 152)**: Both Sensor and Monitor applications MUST provide dedicated guidance and direct action buttons in their Phone Setup overlays (`PhoneSetupOverlay` in `:core-ui`) to configure Do Not Disturb (Notification Policy Access via `Settings.ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS`) and Full-Screen Intent permissions (`Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`), ensuring critical tracker alarms and sirens successfully bypass DND mode and display over locked screens (ISSUE-NOV7.3-O39) (R-ID 152).
*   **1.382 Automatic Sensor Service Startup, Live Uptime Timer & Protected Stop Control (R-ID 153)**: The Sensor application MUST automatically launch `SensorService` on app launch (`AdminActivity`) when permissions are verified, display live service running status and uptime counter (`HH:mm:ss`) on both the admin console card and setup dialog, and present a protected `STOP SENSOR SERVICE` control requiring confirmation dialog verification before issuing `ACTION_STOP_SERVICE` to gracefully terminate background sensing (ISSUE-NOV7.2-O36) (R-ID 153).
